# 15. Providers de LLM

Crie a interface:

```rust
trait LlmProvider {
    async fn generate_structured(
        &self,
        request: LlmRequest,
        schema: JsonSchema,
    ) -> Result<StructuredResponse, LlmError>;

    async fn health(&self) -> ProviderHealth;
}
```

O core não pode depender diretamente de um provider concreto.

Os providers iniciais obrigatórios são:

```text
OpenAI Codex
OpenRouter
```

Não implementar Anthropic como provider inicial.

A arquitetura deve permitir novos providers posteriormente sem alterar `MemoryCompiler`, `GlobalPromoter` ou demais regras de domínio.

---

## 15.1 OpenAI Codex Provider

O provider principal deve permitir utilizar a autenticação existente do Codex e, portanto, o plano Codex/ChatGPT do usuário.

Nome interno:

```text
codex
```

Não solicitar `OPENAI_API_KEY` para esse modo.

Não ler, copiar, persistir ou manipular diretamente tokens OAuth, cookies ou arquivos de credenciais internos do Codex.

A integração deve ocorrer através da interface pública do Codex instalado localmente.

Priorize execução não interativa através do binário `codex`.

Conceitualmente:

```text
MemoryCompiler
      ↓
CodexProvider
      ↓
installed codex CLI
      ↓
existing Codex authentication
      ↓
OpenAI model
```

O provider deve verificar:

```text
codex installed?
codex authenticated?
requested model available?
structured output supported?
```

O `memory doctor` deve apresentar separadamente esses estados.

Quando o usuário ainda não estiver autenticado, retornar erro acionável indicando que deve autenticar o Codex normalmente.

O memory daemon não deve implementar seu próprio OAuth da OpenAI nesta primeira versão.

---

## 15.2 Structured output via Codex

O `MemoryCompiler` depende de JSON estruturado.

O `CodexProvider` deve executar o Codex utilizando suporte de structured output/schema sempre que disponível.

O fluxo deve ser:

```text
JSON Schema generated by memory
        ↓
temporary schema file
        ↓
Codex execution
        ↓
structured final response
        ↓
deserialize
        ↓
schema validation
```

Não parsear Markdown gerado pelo Codex para descobrir memórias.

Não depender de regex sobre texto natural.

Se o Codex retornar resposta inválida:

```text
validate
↓
one bounded retry
↓
fail job
```

Não executar retries indefinidos.

Arquivos temporários de schema devem ser removidos após a execução.

---

## 15.3 Isolamento do Codex usado como provider

Uma chamada feita pelo `CodexProvider` é uma operação interna do memory system.

Ela não pode ser capturada novamente pelos hooks de memória como se fosse uma nova sessão normal.

Caso contrário:

```text
session
→ compiler
→ codex provider
→ hooks
→ new observations
→ compiler
→ loop
```

Implemente mecanismo explícito de exclusão.

Por exemplo, o subprocesso deve receber:

```text
AGENT_MEMORY_INTERNAL=1
```

Todos os adapters devem ignorar eventos cuja execução pertença ao próprio memory runtime.

Essa regra vale para qualquer provider futuro baseado em agent CLI.

---

## 15.4 Working directory do Codex Provider

O provider não deve permitir que o Codex usado para consolidação altere o projeto do usuário.

Execute em ambiente sem permissão de escrita no checkout.

O provider precisa apenas transformar evidência fornecida pelo memory engine em JSON.

Ele não deve:

```text
editar arquivos
executar build
executar testes
usar MCP do projeto
explorar repository
```

O MemoryCompiler deve fornecer no prompt todo o material necessário.

O provider é um serviço de inferência, não um coding agent durante essa operação.

---

## 15.5 Configuração do Codex Provider

Exemplo:

```toml
[llm]
provider = "codex"
model = "default"
```

`model = "default"` significa utilizar o modelo default do Codex instalado.

Também permitir modelo explícito:

```toml
[llm]
provider = "codex"
model = "gpt-5.x-codex"
```

Não hardcode um modelo específico como obrigatório porque a disponibilidade de modelos muda.

A configuração deve ser validada em runtime.

---

## 15.6 OpenRouter Provider

Nome interno:

```text
openrouter
```

Autenticação:

```text
OPENROUTER_API_KEY
```

Nunca persistir a API key em:

```text
Markdown
SQLite
logs
UI
Git
```

Configuração:

```toml
[llm]
provider = "openrouter"
model = "anthropic/..."
api_key_env = "OPENROUTER_API_KEY"
```

Endpoint default:

```text
https://openrouter.ai/api/v1
```

Permitir override:

```toml
[llm]
provider = "openrouter"
model = "..."
base_url = "https://openrouter.ai/api/v1"
api_key_env = "OPENROUTER_API_KEY"
```

O provider deve usar a API compatível com OpenAI e structured output quando o modelo selecionado suportar.

---

## 15.7 Capacidades do provider

Não assuma que todos os modelos possuem as mesmas capacidades.

Defina:

```rust
struct ProviderCapabilities {
    structured_output: bool,
    json_schema: bool,
    embeddings: bool,
}
```

O provider deve detectar ou declarar suas capacidades.

O `MemoryCompiler` exige:

```text
structured_output OR reliable JSON mode
```

Se o modelo configurado não conseguir produzir saída estruturada compatível, `memory doctor` deve sinalizar a configuração como inválida para compilation.

---

## 15.8 Fallback

Permita configurar fallback explícito.

Exemplo:

```toml
[llm]
provider = "codex"
model = "default"

[llm.fallback]
provider = "openrouter"
model = "..."
```

Fluxo:

```text
Codex
  ↓ failure/unavailable
OpenRouter
```

O fallback só deve ocorrer em:

```text
provider unavailable
authentication unavailable
rate/usage limitation
network/provider error
unsupported model capability
```

Não fazer fallback quando o problema for:

```text
invalid memory input
schema bug
internal application error
```

Registrar qual provider processou cada compiler job.

Não gravar credentials.

---

## 15.9 Provider selection

Default recomendado:

```text
codex
```

Se Codex não estiver disponível e OpenRouter estiver configurado:

```text
openrouter
```

Se nenhum provider estiver disponível, o sistema continua funcionando para:

```text
capture
manual memories
search
read
MCP
UI
imports
session storage
project detection
technology detection
```

Jobs que exigem LLM permanecem pendentes ou failed/retryable.

Nunca perder uma sessão apenas porque o provider está indisponível.

---

## 15.10 Embeddings são independentes

O LLM provider e o embedding provider são configurações distintas.

Exemplo:

```toml
[llm]
provider = "codex"
model = "default"

[embeddings]
provider = "openrouter"
model = "..."
api_key_env = "OPENROUTER_API_KEY"
```

O fato de o Codex ser o LLM provider não significa que ele deve fornecer embeddings.

Busca FTS5 continua obrigatória e funcional sem embedding provider.

---

## 15.11 UI de Providers

A tela Settings deve apresentar:

```text
LLM Provider
Model
Status
Authentication status
Fallback provider
Last successful request
Last error
```

Para Codex:

```text
Codex installed
Codex authenticated
Selected model
```

Nunca mostrar tokens ou credenciais.

Para OpenRouter:

```text
API key configured: yes/no
Selected model
Endpoint
```

Nunca mostrar o valor da API key.

---

## 15.12 CLI

Adicionar:

```text
memory provider status
memory provider test
```

`memory provider status` não executa inferência paga.

`memory provider test` executa uma pequena requisição estruturada e valida o resultado.

Também incluir essas verificações em:

```text
memory doctor
```

---

## 15.13 Testes

Criar fake providers para todos os testes normais.

CI nunca deve depender de uma conta Codex real ou OpenRouter real.

Para `CodexProvider`, testar o subprocess boundary com fake executable que simula:

```text
success
not authenticated
binary missing
invalid JSON
schema mismatch
timeout
non-zero exit
```

Para OpenRouter, usar servidor HTTP mock cobrindo:

```text
success
401
429
500
timeout
invalid response
schema mismatch
```

Adicionar teste que garanta que chamadas internas ao Codex possuem:

```text
AGENT_MEMORY_INTERNAL=1
```

e não entram novamente no capture pipeline.
